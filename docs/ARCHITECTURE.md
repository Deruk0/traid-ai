# Предлагаемая архитектура

**Обновление 0.6.0:** реализованы закрытые OHLCV/объёмы, offline и независимое forward-сравнение, watchdog, фоновое получение данных/начислений и цепочка решения → риск → исполнение. Текущая спецификация, команды, результаты и оставшиеся границы — [VALIDATION.md](VALIDATION.md). Описания 0.4/0.5 ниже относятся к предыдущим срезам. Модель остаётся qwen3.5:4b, текущие контекст/промпт — market-summary-v3 / qwen-trader-v3.


Статус: целевое предложение комплекса; текущая реализация — [IMPLEMENTATION.md](IMPLEMENTATION.md). Есть Python-модули данных, локальной Qwen 4B, риска, сессии/исполнения, Alpaca Paper и SQLite. Qwen работает через Ollama; отдельные аналитические сервисы и live отсутствуют. Модель выбирает намерение по подготовленному снимку, без ключей и прямых инструментов брокера.

Первый локальный прототип использует публичные данные и собственный симулятор без аккаунта. 14.10.2026 по отдельному поручению пользователя добавлен BrokerEngine для виртуальных ордеров Alpaca Paper: наследует Engine, повторно использует Risk Engine, владеет pending-ордером и сверяет REST-ответы. Это локальный модуль, а не отдельный сервис; схема ниже остаётся целевым предложением комплекса. [ALPACA.md](ALPACA.md) описывает текущие полномочия, проверки и ограничения. Условия доступа по возрасту и региону отдельно не подтверждены.

## Два контура

В текущем срезе analytics.py реализует обработку проверенных наблюдений bid/ask: окна 1/5/15 минут, качество покрытия, оценку расходов и справочное тестовое правило. Engine сохраняет историю, Store атомарно проецирует разрешённые факты журнала в ограниченную память. qwen.py собирает market-summary-v2 с изменениями, памятью и вариантами действия; фоновый запрос и независимый Risk Engine сохранены. Спецификация фактически реализованных полей и ограничений — [MODELS.md](MODELS.md). Внешняя свечная история, объёмы и аналитические инструменты чтения остаются будущими блоками.

Исследовательский контур готовит и оценивает стратегии: история → гипотеза → формальные правила → backtest → проверка → каталог одобренных стратегий. Может использовать ИИ для поиска и обсуждения идей.

Торговый контур работает только с зафиксированными версиями: текущие данные → признаки → кандидаты → ИИ → Risk Engine → исполнитель → сверка. Он не принимает на лету новый код из исследовательского контура.

## Компоненты и полномочия

| Компонент | Ответственность | Доступ |
| --- | --- | --- |
| Session Controller | Конфигурация, часы, состояния, завершение | Параметры сессии; без произвольной торговли |
| Market Data Collector | Свечи, сделки, стакан, спецификации инструментов | Чтение рыночных данных |
| Data Quality Gate | Свежесть, пропуски, время и согласованность | Данные и отметки качества |
| Feature Engine | Численные признаки, волатильность, ликвидность, режим рынка | Без LLM и биржевых ключей |
| Strategy Registry/Scanner | Версии разрешённых стратегий и допустимые сигналы | Чтение каталога |
| Specialized Analysts | Краткие отчёты по событиям, новостям и контраргументам | Ограниченные источники чтения |
| Context Builder | Компактный снимок для ИИ, ссылки на расчёты | Без торговых ключей |
| Decision Brain | Выбор стратегии/кандидата и намерения | Только структурированная заявка |
| Risk Engine | Размер, лимиты, резервирование, окончательное разрешение | Актуальный портфель и политика |
| Execution Engine | Отправка, отмена и сопровождение ордеров | Единственный торговый доступ |
| Portfolio/Reconciler | Балансы, fills, комиссии, сверка с биржей | Приватные данные чтения |
| Watchdog | Сбой, зависание, инициирование безопасного режима | Управляющие сигналы; без стратегии |
| Journal/UI | История, метрики, состояние | UI-команды только через контроллер |

Специализированный модуль не обязательно является LLM-агентом. Признаки, расчёты и фильтры дешевле и воспроизводимее выполнять кодом. Первый MVP может обойтись одним ИИ и численными обработчиками; аналитик событий и критик добавляются по измеренной пользе.

## Как работает главный ИИ

На входе: время, режим рынка, качество и возраст данных, несколько кандидатов, допустимые стратегии, текущие позиции, свободный бюджет, рисковые ограничения и время до завершения. На выходе: WAIT, REQUEST_ENTRY, REQUEST_EXIT или REQUEST_CANCEL с идентификаторами, причинами и сроком актуальности.

Он вправе выбирать, но не исполнять. Запрос не является ордером. Произвольные символы, стратегия вне каталога, изменение лимитов и неизвестные поля отвергаются. Оценка уверенности LLM не трактуется как вероятность прибыли и не увеличивает размер позиции автоматически.

Вызов — на закрытии выбранной свечи или значимом событии, а не на каждом тике. Конкретная частота определяется стратегией; горизонт пользователя не означает минутный скальпинг. При таймауте или некорректном ответе нет нового входа, сопровождение остаётся активным.

## Контракты данных

Будущие схемы должны иметь `schema_version`, идентификатор сессии, источник, время события, время получения и время, когда информация стала доступна системе. Все машинные времена UTC; интерфейс показывает выбранный часовой пояс, по умолчанию пользователя Europe/Moscow.

| Сущность | Обязательные поля и смысл |
| --- | --- |
| SessionConfig | mode, venue, market_type, capital, currency, instruments, risk_policy_version, deadline_at, entry_cutoff_at, flatten_start_at |
| MarketSnapshot | snapshot_id, as_of, available_at, data_quality, features, provenance, portfolio_version |
| Candidate | candidate_id, strategy_version, instrument, hypothesis, invalidation, expected_holding_time, calculated_costs |
| TradeIntent | decision_id, candidate_id, action, snapshot_id, created_at, expires_at, reason_codes |
| RiskVerdict | decision_id, approve/reject, reason, permitted_quantity, limits_checked, reservation_id, expiry |
| ExecutionEvent | client_order_id, exchange_order_id, state, filled_quantity, fill_price, fees, occurred_at |

Денежные значения рассчитываются Decimal с явной валютой; количества и цены округляются по правилам биржи. Размер, защитный уровень и ожидаемые расходы берутся из формальных правил стратегии и политики, а не из свободного текста LLM.

Перед отправкой разрешение перепроверяется по текущим данным, доступному резерву и состоянию сессии. Срок жизни намерения не должен переживать запрет входов. Один decision_id не порождает повторный вход.

## Предлагаемые технологии

- Python для анализа, контроллеров и интеграции; конкретную поддерживаемую версию выбрать после проверки исполнителя.
- Типизированные схемы для конфигурации и ответов ИИ; кандидат — Pydantic.
- Постоянное хранилище событий и состояния; кандидат PostgreSQL, для одиночного прототипа допустим SQLite при явных ограничениях конкуренции.
- Parquet для исследовательских наборов. Очередь в БД и прямые интерфейсы модулей достаточны сначала; Redis/Kafka не обязательны.
- API и простой локальный интерфейс; кандидат FastAPI. Отдельный frontend выбирать после согласования сценария.
- Несколько процессов по границам доступа: координатор/аналитика, исполнитель, независимый watchdog. Docker Compose и VPS — будущий вариант постоянной работы, не текущая установка.

Это кандидаты, не утверждённые зависимости. Отдельная программа на каждую роль пока не нужна: логические границы можно сохранять в модулях, а исполнение изолировать из-за ключей и восстановления.

## Проверка Freqtrade как исполнителя

Первый технический эксперимент должен проверить границу: наша система управляет сессией и проверяет намерения, Freqtrade единолично владеет ордерами и своей базой. Его собственные входы не могут обходить нашу политику. Наша система не дублирует его ордера напрямую через биржу.

Проверить ограничения внешних команд, сопоставление decision_id с trade/order, запрет новых входов, закрытие и наблюдение частичных fills, защитные выходы без ИИ, рестарт и сверку. Наличие REST-команд не доказывает выполнение всего контракта. При непригодности выбрать отдельный адаптер с минимальными поддержанными операциями.

## Недоверенные источники

Новости и соцсети изолируются от управляющих инструкций. Отчёт содержит источник, время, факты и неопределённость. Внешние тексты не могут вызывать торговые инструменты. Исторический LLM-тест может содержать знания модели о будущем; point-in-time данные сами по себе это не устраняют. Проверять ИИ дополнительно в forward paper и учитывать этот предел интерпретации.
