# Риск, исполнение и завершение

## Свежесть основания и временная защита — 18.10.2026

Подготовленная покупка Qwen сохраняет собственное ai_basis: snapshot_id и observed_at принятого ответа. Перед отправкой, включая повторную проверку после ORDER_SUBMITTING commit, исполнитель проверяет исходный срок max_quote_age по фактическому времени. Обновление котировки или State.ai не продлевает срок. Просроченное основание отменяет ещё не отправленную заявку с ORDER_ABORTED; восстановленное PREPARED без основания также не отправляется. Уже отправленные заявки сохраняют прежний порядок сверки UNKNOWN.

Если задан, MAX_HOLD проверяется без новой или пригодной котировки. С 18.10.2026 для новых сессий он по умолчанию отключён (Config.max_hold_seconds=None); старые сессии сохраняют значение, в том числе исторический час при отсутствующем поле. Это не отключает общий дедлайн, стопы и лимиты потери. Причина заданного MAX_HOLD сохраняется в position_exit_reason; локальная симуляция не создаёт исполнение без принятой цены. У брокера защитный выход допускается после сверки и устранения ожидающей покупки: остаток покупки отменяется, исполнение сверяется, затем продаётся подтверждённое количество. При недоступности сверки отправка остаётся заблокированной, остаток позиции сохраняется. Подробности — [BALANCE_RECONCILIATION.md](BALANCE_RECONCILIATION.md), [EXECUTION_AUDIT_20261018.md](EXECUTION_AUDIT_20261018.md).

## Сопровождение 0.8.0 — 15.10.2026

Новая Config.exit_policy по умолчанию trailing-stop-v1. Стартовый уровень — подтверждённая цена входа × (1 − stop_fraction). Затем position_peak равен максимуму цены входа и принятых bid после входа; stop_price=max(старый стоп, position_peak × (1 − stop_fraction)). Стоп не опускается. Сравнение bid <= stop_price даёт TRAILING_STOP независимо от ИИ и паузы входов. Недостоверные/устаревшие/повторные котировки не изменяют максимум или стоп. Это максимум наблюдений, а не максимум всех сделок биржи между опросами. Локальный fill исполняется по текущему bid с проскальзыванием, а не по придуманной цене стопа.

В State сохраняются position_peak и position_exit_reason; при нулевой подтверждённой позиции они сбрасываются. BrokerEngine не снижает стоп при следующих частичных fills. Если защита срабатывает при незавершённой покупке, причина выхода фиксируется, остаток покупки отменяется, исполнения сверяются и только после этого отправляется один выход на подтверждённый остаток. Отскок цены и рестарт не отменяют срабатывание. CANCEL_PENDING не повторяет DELETE до следующей сверки. UNKNOWN не повторяет POST вслепую. При недоступном брокере выход ждёт подтверждения состояния, остаток явно отражается; обещания закрытия по цене стопа нет.

Config.target_return — необязательный ориентир, а не входной параметр entry_quantity. Функция риска его не читает. Цель не меняет capital/risk_per_trade/max_exposure/loss_limit/drawdown_limit/stop_fraction/max_hold_seconds/deadline. Оценка результата перед закрытием: cash + quantity × bid × (1 − slippage_bps/10000) × (1 − fee_rate) − capital. При известной позиции без котировки оценка неизвестна; поздние начисления могут уточнить результат. Без позиции используется cash − capital. Достижение цели не гарантирует её сохранение к дедлайну.

Совместимость: Config.from_dict без exit_policy использует fixed-stop-v1, без target_return — None. Старый State получает position_peak=0 и position_exit_reason=None. Режим и цель фиксируются при создании, не включаются автоматически в старых сессиях. Скользящий стоп — локальное сопровождение, нативные trailing-ордера Alpaca и новые права API не добавлялись. Общий принцип различия цены стопа и исполнения описан в [Investor.gov](https://www.investor.gov/introduction-investing/general-resources/news-alerts/alerts-bulletins/investor-bulletins-15); конкретная реализация использует наши проверенные bid и прежний Paper-исполнитель.

**Обновление 0.6.0:** реализованы закрытые OHLCV/объёмы, offline и независимое forward-сравнение, watchdog, фоновое получение данных/начислений и цепочка решения → риск → исполнение. Текущая спецификация, команды, результаты и оставшиеся границы — [VALIDATION.md](VALIDATION.md). Описания 0.4/0.5 ниже относятся к предыдущим срезам. Модель остаётся qwen3.5:4b, текущие контекст/промпт — market-summary-v3 / qwen-trader-v3.


Статус: требования целевой системы. Реализованный Paper-срез 0.4.0 описан ниже и в ALPACA.md; остальные функции остаются предложением. Профили риска пользователя ещё не выбраны.

Текущее предложение с учётом возраста пользователя — собственный paper-симулятор. Риски, ордера и дедлайн сначала проверяются в нём с виртуальными средствами. Описанная ниже работа с реальной биржей отложена до подтверждения допустимости такого доступа; торговые ключи сейчас не нужны.

## Политика риска

Профиль риска — численная политика с версией, фиксируемая на старте сессии. Главный ИИ не может менять её. Если настройка отсутствует или противоречит другой, запуск отклоняется.

Проверки нового входа: разрешённый инструмент и стратегия, корректность данных, актуальность намерения, здоровье биржи/исполнителя, срок до завершения, свободные средства, риск на сделку, общая экспозиция, концентрация, число позиций и ожидаемые расходы. Учитывать уже открытые ордера и зарезервированный бюджет. Резервирование атомарно: два одновременно одобренных сигнала не могут потратить один и тот же лимит.

Лимит потерь и просадка считаются по equity выделенной сессии с реализованным и нереализованным результатом и комиссиями. База отсчёта, оценка активов и перевод комиссий в расчётную валюту фиксируются. Плохие данные оценки блокируют новые входы. Ограничение потерь — триггер действий, а не гарантия, что фактический убыток не превысит число при скачке цены.

Для спота без плеча базовая оценка количества:

`quantity <= allowed_loss / (abs(entry_price - stop_price) + estimated_cost_per_unit)`

Затем применяются лимиты средств/экспозиции, ликвидность и правила минимального ордера. Нулевое или некорректное расстояние до stop отклоняется. Это расчёт ожидаемого риска: gap, slippage и недоступность биржи могут дать больший убыток. Для фьючерсов понадобится отдельный расчёт контрактов, маржи, funding и ликвидации; эта формула его не заменяет.

Защитные ордера на стороне биржи использовать там, где выбранная биржа/рынок это поддерживает и проверена семантика. Их наличие не заменяет контроллер дедлайна и сверку. Решение об аварийном выходе не ожидает ответа ИИ.

## Дедлайн

`deadline_at` — целевое время закрытия. `entry_cutoff_at` — прекращение новых входов. `flatten_start_at` — начало обязательного сворачивания. Оба момента не позже deadline; их порядок и буферы явно проверяются. Обычно входы прекращаются до начала сворачивания.

Для каждой сделки ожидаемое удержание и запас на выход должны укладываться в оставшееся разрешённое время. При короткой сессии стратегия с горизонтом нескольких дней не допускается.

При начале завершения:

1. Зафиксировать состояние FLATTENING, запретить входы, аннулировать неиспользованные разрешения и резервы.
2. Отменить входные заявки и дождаться подтверждения либо сверить их состояние. Учитывать исполнение, которое произошло одновременно с отменой.
3. Получить актуальные управляемые остатки, активные и защитные ордера.
4. Закрывать фактические остатки по заранее выбранной политике. Не продавать исходные активы пользователя, не принадлежащие сессии.
5. После каждого fill обновлять остаток. Не снимать единственную защиту без согласованного перехода; не оставлять защитный ордер после закрытия, если он может создать лишнюю операцию.
6. Сверить баланс/позиции и отсутствие активных ордеров сессии, записать комиссии и результат.

Политика выхода должна заранее определить компромисс между скоростью и ценой: лимитный выход с ограниченным ожиданием, возможность перехода к рыночному, предел допустимого ухудшения цены и действия при его превышении. Нельзя одновременно обещать жёсткий предел проскальзывания и безусловное закрытие к сроку. Эта политика пока не выбрана.

## Состояния сессии

| Состояние | Значение |
| --- | --- |
| DRAFT | Параметры ещё не проверены |
| READY | Проверены параметры и готовность инфраструктуры |
| RUNNING | Разрешены входы в пределах политики |
| PAUSED_ENTRIES | Входы запрещены; сопровождение и выходы продолжаются |
| FLATTENING | Отмена входов, закрытие управляемых остатков, сверка |
| CLOSED | Биржа подтвердила закрытие и отсутствие активных ордеров сессии |
| CLOSED_WITH_RESIDUAL | Есть только явно учтённый остаток ниже минимального ордера; это не полное закрытие |
| UNRESOLVED | Закрытие/сверка не подтверждены; управление восстановлением и сигнализация продолжаются |

Пауза входов не сдвигает дедлайн. По deadline без подтверждения переходить в UNRESOLVED, а не CLOSED. Причиной могут быть outage биржи, rate limit, приостановка инструмента или невозможность продать остаток. Состояние и причина показываются пользователю. После восстановления продолжить сверку и выход согласно политике; без самовольного возобновления входов.

## Учёт ордеров и восстановление

Перед отправкой сохранить намерение и уникальный client_order_id в устойчивом хранилище. После ответа сохранить биржевой ID и состояние. Идентификаторы не использовать повторно для новых логических ордеров.

Отслеживать SUBMITTING, OPEN, PARTIALLY_FILLED, FILLED, CANCEL_PENDING, CANCELED, REJECTED и UNKNOWN. При timeout/5xx состояние может быть неизвестным: проверить stream и запросить ордер/историю, прежде чем решать вопрос повторения. Биржевой client_order_id помогает идентификации, но не считается универсальной гарантией exactly-once.

После рестарта сначала сверять открытые ордера, fills, комиссии и баланс с журналом. До завершения сверки входы запрещены. Неизвестный внешне созданный ордер требует разрешения расхождения, а не автоматического присвоения его сессии. Выделенный аккаунт/субаккаунт предпочтительнее смешанного ручного и автоматического управления.

Один активный владелец исполнения: блокировка/lease с защитой от второго экземпляра и устаревшего владельца. Проверять эту гарантию выбранным механизмом перед live. Watchdog требует действий через того же владельца, а не создаёт параллельный поток торговли.

По возможности сочетать приватный stream с периодической REST-сверкой: stream может пропустить события. Повтор событий не должен дважды учитывать fill или комиссию.

## Поведение при сбоях

| Событие | Реакция |
| --- | --- |
| Устаревший рынок | Запрет входов; сопровождение по проверенным доступным данным |
| LLM не отвечает/ошибка схемы | Нет нового входа; стопы, дедлайн и сверка продолжаются |
| Расходы LLM исчерпаны | Прекратить необязательный анализ; продолжать управление риском |
| Достигнут лимит потери | Запрет входов и завершение по политике |
| Неизвестен результат ордера | UNKNOWN, сверка; никаких слепых повторов |
| Потеря приватного stream | REST-сверка с ограничениями частоты; при недостаточной уверенности блокировать входы |
| Биржа недоступна | Запрет входов, ограниченные повторы сверки/выхода и явное UNRESOLVED |
| Устойчивое хранилище недоступно | Не отправлять новые входы; аварийный порядок сопровождения определить и испытать до live |
| Завершение процесса | Восстановление и сверка; защита на бирже, если она была подтверждённо установлена |

## Граница доступа

Реализованный срез 0.4.0 (14.10.2026): BrokerEngine управляет BTC/USD только в Alpaca Paper. Ограничения проверяются до отправки; подтверждённые fills и сверенный net-остаток учитываются отдельно. Намерение и SUBMITTING сохраняются до POST; одна pending-заявка и блокировка аккаунта исключают второй исполнитель. Отсутствующий UNKNOWN не повторяется вслепую: правило полной повторной сверки описано в ALPACA.md. Посторонние позиции/заявки останавливают действия. Нулевая позиция без завершённой сверки не означает CLOSED. Dust остаётся UNRESOLVED, CLOSED_WITH_RESIDUAL пока не реализован. Watchdog и сверка поздних activities остаются будущей работой; fees/PnL Paper-отчёта предварительные.

ИИ и аналитики не получают ключи. Исполнитель получает только необходимые торговые права, без вывода средств; приватные данные чтения можно отделить. UI не открывает прямой доступ к исполнителю. Журнал скрывает секреты.

Причина отдельного учёта UNKNOWN подтверждена [документацией Binance Spot REST](https://developers.binance.com/en/docs/products/spot/rest-api): timeout и серверная ошибка не всегда означают отсутствие исполнения. Это пример API-семантики, а не выбор Binance для проекта. Проверено 13.10.2026.
